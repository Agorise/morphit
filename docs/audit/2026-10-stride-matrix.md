# Morphit threat model — STRIDE + data-flow diagram (2026-10)

The current threat model. It replaces the 2026-05 STRIDE matrix and the
2026-09 v1.16 delta model (both retired). It was
built from the code, then updated after the 2026-10 fixes: every row
says what the code does now and names the guard that proves a fix.

Status legend:

- **FIXED** — the 2026-10 fix is in the tree;
  the named test or smoke fails on the code before the fix.
- **PROVEN-T** — a mitigation that predates this round, exercised by a
  named test or smoke.
- **ASSERTED** — the mitigation exists in code but no test exercises the
  behaviour.
- **OPEN** — not stopped by code; the reason (accepted, decision pending,
  operator action) is given.

Companion documents: `2026-10-attack-tree.md` (attacker goals) and
`2026-10-red-team-narrative.md` (end-to-end campaigns).

## 1. Attacker classes

| ID     | Attacker                                                | Typical capability                                                 |
| ------ | ------------------------------------------------------- | ------------------------------------------------------------------ |
| A-NET  | Network observer (ISP, Tor guard, exit, transit)        | sees clearnet IP/timing; cannot break TLS/Tor                      |
| A-WEB  | Any website the victim also visits                      | runs JS in the victim's browser, cross-origin                      |
| A-VIS  | A hostile visitor of an instance (clearnet, Tor or I2P) | arbitrary HTTP to the public edge                                  |
| A-PEER | A hostile federation "instance"                         | registers on chain, answers probes, receives pushes                |
| A-RPC  | One hostile or compromised Blurt RPC endpoint           | answers any JSON-RPC call with anything                            |
| A-OP   | A hostile instance operator                             | full control of one box, its DB, logs, frontend bytes              |
| A-SUP  | Supply-chain attacker                                   | Forgejo primary, CI runner, mirror, npm/Docker registry, IPFS peer |
| A-LEG  | Legal / seizure                                         | takes a box's disk (DB, journald, Docker volumes, backups)         |

### 2.3 Trust boundaries (TB)

| TB6  | Instance ↔ other third parties (push services, explorers, price/FX, Matrix, apt/npm/Docker)                 |

## 7. Known open items

- Agreement between RPC operators (posting keys, fee-relevant blocks, snapshot
  and directory ops): operators are counted by the node list's names; the default hidden-network nodes are run by the project, so on a hidden-only node this agreement is not between independent parties. The signatures on
  release, directory and snapshot ops are what stop forgery there.
- Ordinary user ops are still applied from one RPC node's block (E1); the
  periodic chain-consistency sample is an alarm, not a filter.
- The attestation phase is node-local but decides a consensus verdict.
- A hostile operator can serve a backdoored build; nothing in the page can
  stop that. Users' defence is choosing operators, the signed release, and
  running their own instance.
- Chat has no forward secrecy and public metadata (who, when, which order,
  read receipts) — documented, by design.
- Builds are not byte-reproducible.
